TryBox Stremio Addon 开发全记录

一篇从探针到生产部署的完整技术复盘。包含协议逆向、架构设计、缓存分层、ID 兼容、踩坑与技巧。既是本项目的技术沉淀，也可作为 Stremio Addon 开发的参考。

一、项目背景与目标

1.1 缘起

TryBox（trybox.app）是一个影视聚合站点，提供影视元数据、多源播放链接、中英文字幕。它没有公开 API，所有请求走 /_serverFn/ 下的加密端点，payload 是自定义的 t/p/k/v/a 结构。

目标：把 TryBox 的数据封装成 Stremio Addon，让用户能在 Stremio 客户端里浏览、搜索、看详情、加载字幕、播放流。同时开发一个独立的 Nuvio Provider，让 Nuvio 用户也能访问 TryBox 的流。

1.2 约束

约束 说明
国内访问 用户主要在国内，必须考虑网络可达性
Vercel 部署 选择 Vercel 而非 Cloudflare Workers
Edge Runtime 必须使用 Vercel Edge Function，零第三方运行时依赖
Upstash 共享 多个项目共用一个 Upstash Redis，必须用 APP_PREFIX 隔离
成本 免费层额度内运行
规范 遵守已有的项目开发规范（配置分层、缓存 TTL、日志分级等）

二、协议逆向：探针的设计与实施

2.1 为什么先写探针

TryBox 的 API 是自定义协议。直接写 addon 会面临：

  • 不知道请求 payload 的确切结构
  • 不知道响应的数据字段和类型
  • 不知道 stream 链接是否带鉴权
  • 不知道字幕接口的参数组合

探针的本质：一个独立的诊断脚本，**只做”发请求 + 打印结果”**，不参与业务逻辑。它的职责是：

  1. 验证 API 可用性
  2. 探明请求/响应结构
  3. 评估数据完整性和响应时间
  4. 为后续开发提供”事实依据”

探针原则：不猜、不想当然、以实际返回为准。

2.2 探针的整体设计

我实现的探针脚本（probe.js）覆盖 5 个核心接口：

探针 用途 关键发现
catalog 首页各板块数据 一次请求返回全部板块（713KB），可复用
search 关键词搜索 支持 multi / movie / tv 三种类型
meta 影片详情 TV 类型只返回 seasons 列表，不含 episodes
subtitle 字幕列表 需要 imdb_id，支持语言过滤
stream 播放链接 POST 请求（不是 GET），需要 Bearer Token

2.4 探针的三大产出

产出 1：请求 payload 模板

产出 2：响应结构地图

接口 顶层字段 数组板块
Catalog trending, popular, topRated, secondary, tertiary, presets.* 12 个数组
Meta id, imdb_id, seasons, cast, videos, … 5 个数组
Stream meta, links, mbp_links, beta_links 3 个数组

产出 3：关键事实

  1. Catalog 一次请求返回全部板块（713KB），所有 catalog 可共享同一份缓存
  2. Meta 的 TV 类型需要额外请求 episodes 接口（每季一次）
  3. Stream 是 POST 请求，必须带 Authorization: Bearer header
  4. Stream 链接部分带 IP 查询参数（IP 校验），部分不带
  5. 字幕接口用 imdb_id，不用 tmdb_id

2.5 探针的补充：episodes 探针

第一轮探针没覆盖 episodes（剧集列表），导致后面写 meta 时遇到问题。补充探针后确认：

  • episodes 接口独立于 meta
  • 每季一次请求（不能一次拿全部季）
  • 响应包含 episode_number、name、air_date、still_path 等

教训：探针要覆盖所有下游接口，不能只测主接口。

2.6 探针的最大价值

**避免”想当然”**。举例：

  • 如果没跑探针，会以为 stream 是 GET 请求 → 405 错误
  • 如果没跑探针，会以为 catalog 每个板块需要单独请求 → 浪费 11 倍请求
  • 如果没跑探针，会以为 stream 链接都能用 → 用户播放失败率极高
  • 如果没跑探针，会以为 subtitle 用 tmdb_id → 永远查不到字幕

探针是事实来源，代码是对事实的翻译。

3.3 关键设计决策

决策 1：为什么用 trybox_{tmdbId} 而不是 tt{imdbId}

  • Catalog 返回的 id 必须是 TryBox 能直接用的 id
  • TryBox 的 catalog 只返回 TMDB ID
  • 如果 catalog 用 tt ID，就需要把 125 个 TMDB ID 都转成 IMDb ID（要么批量查 TMDB，要么逐条查 meta，都很慢）
  • 保留 trybox_ 前缀做内部链路，额外支持 tt 做外部联动，两全其美

决策 2：为什么单独设计 token 管理

  • TryBox 的 stream 接口需要 Bearer Token
  • Token 来自 Supabase，refresh_token 是一次性的（用一次就失效）
  • 必须持久化（内存 + Redis），否则每次请求都拿旧 token → 报 refresh_token_already_used
  • 三级刷新：内存 → 用户配置 → Redis → refresh 刷新 → access 刷新 → Bark 告警

决策 3：为什么 Token 要同时存内存和 Redis

  • 内存：同一 isolate 内快速复用，省 Upstash 请求
  • Redis：跨 isolate、跨请求持久化
  • 写入时同时写两份，读取时先查内存、再查 Redis
  • **access_token 检查 JWT exp**，未过期直接用，避免浪费 refresh_token

5.3 缓存 key 设计

关键决策：

  • **Catalog 用同一个 key catalog:home**：因为 TryBox 一次返回全部板块，所有 catalog 共享
  • **Episodes 用单个 key episodes:{tvId}**：包含全部季，而不是每季一个 key
  • **tt 转换用 imdb_to_tmdb:{ttId}**：全站共享

收益对比（Meta series）：

方案 冷启动请求 热启动请求
每季一个 key 1 次 meta + N 次 episodes + 2(N+1) 次 Upstash 1 + N 次 Upstash
单个 key 1 次 meta + N 次 episodes + 4 次 Upstash 2 次 Upstash

继承之战 4 季：从 5 次 Upstash 降到 2 次。

六、Token 管理的完整方案

6.1 需求分析

TryBox 的 stream 接口需要 Bearer Token：

  • Token 来自 Supabase Auth
  • refresh_token 是一次性的（用一次就返回新的，旧的立即失效）
  • access_token 有效期 1 小时
  • 必须持久化，否则每次请求都拿旧 token 撞 already_used
  • 失效时要告警给管理员

6.2 三级刷新流程

关键设计：

  • **先检查 JWT exp**，未过期就用，避免浪费 refresh_token
  • 同时写内存和 Redis，跨请求持久化
  • Bark 告警：token 全失效时通知管理员

十、附录：Stremio Addon 开发注意事项清单

10.1 Manifest 规范

  • id 必须全局唯一，建议用反向域名（如 community.trybox）
  • version 语义化版本
  • resources 用对象数组声明，每个资源单独配 types 和 idPrefixes
  • catalogs 里的 extra 声明 search / genre / skip
  • idPrefixes 不能包含冒号（Stremio 用 : 分隔 season/episode）
  • behaviorHints.configurable: true 开启配置页

10.2 Catalog 规范

  • metas 数组里的每一项必须有 id、type、name
  • poster 用 https://image.tmdb.org/t/p/w500{path}
  • background 用 https://image.tmdb.org/t/p/original{path}
  • releaseInfo 建议只放年份
  • imdbRating 是字符串（不是数字）
  • 一个 catalog 可以同时支持 movie 和 series（在 manifest 里声明两次）

10.3 Meta 规范

  • meta.id 必须与请求的 id 一致（关键）
  • meta.type 是 movie 或 series
  • series 类型必须有 videos 数组
  • videos[].id 格式：{metaId}:{season}:{episode}
  • videos[].season 和 videos[].episode 是数字
  • meta 失败时返回 { meta: null }，不要返回 debug 信息

10.4 Stream 规范

  • 每个 stream 必须有 url / externalUrl / infoHash / ytId 之一
  • name 是分类名（如 “TryBox · MovieBox”）
  • title 是流描述（如 “1080P · 文件名”）
  • quality 是清晰度（1080p / 720p / 4K / ORG）
  • bingeGroup 用于剧集质量记忆
  • 诊断信息放 url，中文原文不编码

10.5 Subtitle 规范

  • subtitles[].id 必须唯一
  • subtitles[].url 是字幕下载地址
  • subtitles[].lang 是 ISO 639-1 两位码（如 zh、en）
  • 不要返回没有 lang 的字幕

10.6 ID 规范

  • ID 前缀不含冒号
  • ID 前缀短、小写、有意义
  • Catalog / Meta / Stream 的 ID 必须一致
  • tt 前缀保留给 IMDb ID

10.7 部署规范

  • Edge Runtime 零第三方运行时依赖
  • 用 APP_PREFIX 隔离环境
  • 缓存 key 统一前缀
  • 绑定自定义域名（国内）
  • 加 Cache-Control 响应头（CDN 缓存）
