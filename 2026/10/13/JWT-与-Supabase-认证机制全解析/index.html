3.3 为什么用 ES256 而非 HS256

  • HS256 是对称加密，服务端和客户端共享同一个 secret，一旦泄露全线崩溃。
  • ES256 是非对称，Supabase 持有私钥，任何人可用公钥验证，服务端不需要持有任何 secret。
  • 这也是 Supabase 新版默认用 ES256 的原因。

3.3.1 HS256 与 ES256 的完整对比

JWT 支持多种签名算法，Supabase 历史上用过 HS256，新项目默认用 ES256。两者在安全性、密钥管理、验签方式上有本质区别：

维度 HS256 ES256
全称 HMAC with SHA-256 ECDSA with SHA-256 (P-256)
密钥类型 对称：同一个 secret 用于签名和验签 非对称：私钥签名，公钥验签
签名方 持有 secret 的一方 持有私钥的一方（Supabase）
验签方 必须持有同一个 secret 只需持有公钥
密钥分发 secret 必须安全地分发给所有验签方 公钥可公开发布（JWKS）
泄露风险 secret 一旦泄露，攻击者可伪造任意 token 私钥泄露才危险；公钥泄露无影响
JWKS 支持 ❌ 不支持（没有公钥概念） ✅ 支持（通过 /.well-known/jwks.json 分发）
算法标识 HS256 ES256
签名长度 较短（32 字节） 较长（64 字节）
计算开销 较低 略高（但可忽略）
Supabase 默认 旧项目 新项目默认
典型场景 单体应用、内部服务 多服务、微服务、第三方验签

为什么 Supabase 新项目改用 ES256？

  1. 服务端无需持有 secret：TryBox 只需从 Supabase 的 JWKS 端点拉公钥，不用保管任何密钥，减少了密钥泄露面。
  2. 多服务友好：任何想验证 Supabase JWT 的服务（TryBox、第三方集成方）都可以独立拉公钥，不需要向 Supabase 索要 secret。
  3. 符合 OIDC 标准：OIDC 规范推荐非对称签名，Supabase 遵循此实践。
  4. 私钥集中管理：只有 Supabase Auth 服务持有私钥，攻击面收窄。

HS256 的遗留问题：

  • 如果你在旧项目里看到 alg: HS256，说明用的是 Supabase 的 JWT secret 对称签名。
  • 验签方必须持有 secret，secret 泄露即全线崩溃。
  • Supabase 已逐步迁移到 ES256，新项目不再暴露 HS256 的 secret。

看 JWT Header 的 alg 字段：

  • ES256：非对称，用 JWKS 验签。
  • HS256：对称，用 secret 验签（旧项目）。

四、JWT 中关键字段详解

案例中 Payload 包含多个时间戳和会话标识，其中 exp、iat、amr.timestamp、session_id 是每次刷新或登录时可能变动的字段。下面逐一剖析。

4.1 exp：过期时间

  • 含义：JWT 的过期时间（Expiration Time）。
  • 来源：Supabase Auth 服务器在签发时，用 服务器当前时间 + 有效期 计算得出。
  • 默认有效期：Supabase 默认 access_token 有效期为 3600 秒（1 小时），可在项目设置中修改。
  • 验证：exp - iat = 1791710467 - 1791706867 = 3600，正好 1 小时。
  • 时间性质：Unix 时间戳（秒），UTC，服务器时间。
  • 作用：服务端验证 Token 是否过期；过期后需要用 refresh_token 换新的 access_token。

4.2 iat：签发时间

  • 含义：Issued At，JWT 的签发时间。
  • 来源：Supabase Auth 服务器在生成 Token 时写入的服务器当前时间。
  • 时间性质：Unix 时间戳（秒），UTC，服务器时间。
  • 作用：判断 Token 新旧；与 exp 配合计算有效期。
  • 变动：每次刷新 Token，iat 都会更新。

4.3 amr.timestamp：认证方法时间戳

  • amr：Authentication Methods Reference，认证方法引用。
  • **method: “otp”**：表示用户通过 OTP（一次性密码/邮箱验证码）登录。
  • timestamp：该认证方法发生的服务器时间，Unix 时间戳，UTC。
  • 来源：Supabase Auth 在用户完成 OTP 验证时记录。
  • 与 iat 的关系：
    • amr.timestamp = 1791694481
    • iat = 1791706867
    • 差值 = 12386 秒 ≈ 3.44 小时。
    • 说明用户最初通过 OTP 登录是在约 3.44 小时前，而当前 Token 是后来刷新得到的（iat 是刷新时间）。
  • 作用：记录认证事件；用于多因素认证（MFA）判断；服务端可据此决定是否要求重新认证。
  • 变动：重新登录或重新进行 OTP 验证时，timestamp 会更新。

4.4 amr 数组可能有多个元素

amr 是数组，因为一个会话可能经历多次认证：

多元素场景：

  • 用户先用密码登录，再完成 MFA（TOTP/OTP），会有两条记录。
  • aal（Authenticator Assurance Level）反映最高认证等级：
    • aal1：单因素
    • aal2：多因素（如密码 + TOTP）

服务端可据此判断是否需要敏感操作二次验证。

4.5 session_id：会话 ID

  • 含义：Supabase Auth 为这次登录会话分配的唯一标识符，UUID 格式。
  • 来源：用户登录成功时，由 Supabase Auth 服务器生成。
  • 作用：
    • 标识一次完整的登录会话。
    • 刷新 Token 时，session_id 保持不变。
    • 登出时，服务端会使该 session_id 失效。
    • 可用于会话管理、强制下线、审计等。
  • 变动：每次重新登录会生成新的 session_id；刷新 Token 不会改变。

4.6 role 与 aud 的区别

容易混淆的两个字段：

字段 含义 Supabase 中的典型值
aud Audience，令牌的预期接收方 authenticated
role Role，用户的角色 authenticated / anon / service_role
  • aud 用于跨服务验证：TryBox 验签时会检查 aud === 'authenticated'，防止匿名 token 混入。
  • role 用于权限控制：PostgreSQL 的 RLS（行级安全）策略里会用到 role。

两者可能同值但语义不同，不要混淆。

4.7 is_anonymous 字段

Supabase 支持匿名登录（Anonymous Sign-ins），即无需邮箱/密码，直接获取临时身份。此时 is_anonymous: true，role: 'authenticated'，aud: 'authenticated'，但 email 为空。

TryBox 若允许匿名用户，需在服务端额外判断 is_anonymous，避免匿名用户访问付费内容。

4.8 时间戳性质总结

字段 含义 来源 时间类型 是否变动
exp 过期时间 服务器签发时计算 Unix UTC 每次刷新变
iat 签发时间 服务器当前时间 Unix UTC 每次刷新变
amr.timestamp 认证方法发生时间 服务器记录 OTP 验证时刻 Unix UTC 重新登录变
session_id 会话 ID 登录时生成 UUID 重新登录变

关键结论：所有时间戳均为服务器时间（Unix UTC），不是客户端本地时间。客户端只负责接收和存储，无法参与生成或篡改。

4.9 expires_in 与 expires_at 的区别

你提供的 session JSON 里有：

字段 含义 类型
expires_in 有效期相对时长（秒） 相对值
expires_at 过期绝对时间戳（秒） 绝对值

expires_at = 当前时间戳 + expires_in。

JWT 里的 exp 是 UNIX 秒级时间戳，**session.expires_at** 也是秒级时间戳，两者应该一致（但如果刷新有延迟可能略有差异）。

5.6 使用 supabase-js 的简化写法

六、登录后 Authorization 是否”确定”了？

6.1 登录成功那一刻确定了什么

用户通过 OTP 验证成功后，Supabase Auth 返回一个 session，包含：

  • access_token：JWT，即第一个 access token。
  • refresh_token：用于后续换新 token。
  • expires_in：通常 3600 秒。
  • user：用户信息。

此时确定了：

  • 会话身份（sub、role、session_id、amr.timestamp）。
  • 初始 access_token。
  • refresh_token。

6.2 但 Authorization 头不是固定不变的

access_token 有有效期，通常 1 小时。过期后，客户端会用 refresh_token 向 Supabase 请求新的 access_token。

刷新后：

字段 是否变化 说明
access_token 变 新的 JWT
iat 变 新的签发时间
exp 变 新的过期时间
签名 变 因为内容变了
refresh_token 变 rotation 机制，旧的立即失效
session_id 通常不变 还是同一个登录会话
amr.timestamp 不变 认证事件没有重新发生
sub、email、role 不变 用户身份不变

因此：

Authorization 头的值一直在变，但代表的还是同一个用户、同一个会话。

6.3 每次请求都是动态取当前 Token

supabase-js 会自动：

  1. 检查 token 是否快过期。
  2. 如果快过期，先用 refresh_token 刷新。
  3. 把最新的 access_token 返回。

所以 Authorization 头不是登录时写死的一个字符串，而是每次请求前根据当前会话状态动态生成的。

6.4 什么时候会真正”重新确定”

以下情况会生成全新的会话和 token：

  • 用户重新登录（重新输入 OTP）。
  • 用户登出后再登录。
  • 会话被服务端撤销。
  • refresh_token 失效或过期。

这时：

  • 新的 session_id 生成。
  • 新的 amr.timestamp。
  • 新的 refresh_token。
  • 新的 access_token 序列。

七、access_token 与完整 JWT 的关系

7.1 access_token 就是完整 JWT

登录成功后拿到的 access_token 本身就是一个完整的 JWT，不需要再”进一步获取”。

其中：

  • access_token：完整的 JWT，格式为 header.payload.signature。
  • refresh_token：不是 JWT，是普通字符串，用于刷新。

7.1.1 id_token 与 access_token 的区别

在 Supabase 的 OIDC（OpenID Connect）模式下，登录成功后可能同时返回 id_token 和 access_token。两者都是 JWT，但用途和内容有本质区别：

维度 access_token id_token
用途 调用 API（授权） 标识用户身份（认证）
受众 aud 资源服务器（如 TryBox） 客户端应用（如 TryBox 前端）
使用位置 Authorization: Bearer <access_token> 通常只在前端解析，不发给业务服务
是否发给第三方 ✅ 发给资源服务器 ❌ 不发给资源服务器
有效期 短（默认 1 小时） 短（通常与 access_token 一致）
是否可刷新 ✅ 用 refresh_token 刷新 ✅ 随 access_token 一起刷新
包含用户信息 部分（sub、email 等） 完整（name、picture、email_verified 等）
标准 OAuth 2.0 OIDC
Supabase 默认返回 ✅ 总是返回 ⚠️ 仅在 OIDC 流程中返回

在 TryBox 案例中：

  • 你贴的 Authorization: Bearer eyJhbGci... 里的 token 是 access_token。
  • 它用于调用 TryBox 的 Server Function，TryBox 服务端验证它来确认用户身份。
  • id_token 如果存在，通常只用于前端显示用户信息（如头像、昵称），不会发给 TryBox 服务端。

两者的 JWT 结构对比：

关键区别：

  1. aud 不同：

    • access_token 的 aud 是 authenticated（资源服务器受众）。
    • id_token 的 aud 是客户端应用 ID（client_id）。

  2. 用途不同：

    • access_token 用于授权：证明”你有权访问 TryBox”。
    • id_token 用于认证：证明”你是谁”。

  3. 接收方不同：

    • access_token 发给 TryBox 服务端。
    • id_token 只在前端使用，不发给服务端。

  4. 包含信息不同：

    • id_token 通常包含更完整的用户资料（姓名、头像等）。
    • access_token 只包含必要的授权信息。

Supabase 中的实际行为：

  • 使用 supabase.auth.signInWithOtp 或 verifyOtp 时，返回的 session 中：
    • 一定有 access_token。
    • 如果启用了 OIDC，可能也有 id_token（在 session.id_token 或 data.id_token 中）。
  • 使用 supabase.auth.getSession() 获取的 session 通常只含 access_token。
  • 使用 supabase.auth.getUser() 可以获取完整用户信息（通过 access_token 调用 /auth/v1/user 端点）。

为什么容易混淆？

  • 两者都是 JWT，都有三段结构。
  • 两者都由 Supabase 签发，iss 相同。
  • 两者的 sub 相同（都是同一个用户）。
  • 但 aud 不同，用途不同，接收方不同。

安全提醒：

  • access_token 不能给第三方：它等同于登录态。
  • id_token 也不能随意公开：虽然用途不同，但它也包含用户身份信息，泄露可能导致隐私问题。
  • 不要混用：不要把 id_token 当 access_token 用，反之亦然。TryBox 服务端只认 access_token。

如何区分你拿到的是哪个？

  1. 看 aud 字段：

    • authenticated → access_token。
    • 客户端 ID → id_token。

  2. 看使用位置：

    • Authorization: Bearer 头 → access_token。
    • 前端解析显示用户信息 → id_token。

  3. 看返回来源：

    • session.access_token → access_token。
    • session.id_token 或 data.id_token → id_token。

结论：

  • access_token 用于调用 API，受众是资源服务器，必须发给 TryBox。
  • id_token 用于标识用户，受众是客户端应用，只在前端使用。
  • 两者都是 JWT，但用途、受众、接收方不同，不能混用。
  • TryBox 案例中，Authorization: Bearer 里的是 access_token，不是 id_token。

8.1 access_token 会过期

这是全文最容易被误解、也最关键的修正点。

你的油猴脚本里有一条极其重要的注释：

这是 Supabase 的 refresh token rotation（轮换）机制：

  • 每次用 refresh_token 换新 token 时，旧的 refresh_token 立即失效，Supabase 返回一个全新的 refresh_token。
  • 如果客户端推送的是”当前页面 localStorage 里的旧 refresh_token”，可能会覆盖掉其他服务/其他标签页刚刚推送的新 refresh_token，导致整个系统 refresh_token 失效。

**这解释了为什么系统要设计成”服务端集中管理 refresh_token”**：refresh_token 是单点的、一次性的、易失效的，必须由唯一权威来源管理。

8.5 refresh_token 也会过期吗

会。refresh_token 也有有效期，并且可以被撤销。具体时长取决于 Supabase 项目的配置，通常比 access_token 长很多。

以下情况会让 refresh_token 失效：

  • 超过配置的有效期。
  • 用户主动登出。
  • 管理员撤销会话。
  • 检测到 refresh token 重用（如果启用了 rotation 和 reuse detection）。
  • 用户修改密码等安全事件。

如果 refresh_token 也失效了，就无法再自动刷新，必须重新登录。

8.6 为什么设计成会过期

  • 限制泄露风险：access_token 一旦泄露，最多只能用 1 小时。
  • 可撤销会话：服务端可以通过 refresh_token 撤销长期访问。
  • 最小权限：短期凭证减少被滥用窗口。
  • 符合 OAuth 2.0 / OIDC 最佳实践。

9.1 完整流程图

9.2 逐层剖析

层 来源 职责 写回策略
1 内存缓存 最快路径，命中即零延迟 无需写回
2 用户配置 允许用户手动覆盖（调试/应急） 命中后写内存

设计哲学：每一层都在”更快”和”更可靠”之间权衡。前 3 层是读取优化，第 4-5 层是写入/续期，第 6 层是兜底告警。这比单纯用 supabase-js 自动刷新要健壮得多，适用于服务端多实例共享 token 的场景。

9.3 第 5 层”用旧 access_token 刷新”的特殊性

这是整个降级链中最容易被忽略、也最精妙的一层：

  • 标准路径是”refresh_token → 新的 access_token + 新的 refresh_token”。
  • 但如果 refresh_token 已经失效（比如被其他实例用过一次），标准路径就走不通。
  • 此时尝试用旧的 access_token 去换新的 token。Supabase 在某些场景下允许尚未过期的 access_token 触发刷新（具体取决于配置），这是最后的续期机会。
  • 成功则恢复；失败则进入告警层。

9.4 第 6 层：Bark 告警与诊断 stream

Bark 是 iOS 上的一个开源推送工具（通过 HTTP API 推送到 iPhone）。这说明系统设计者：

  • 把 token 获取失败视为需要立即人工介入的严重事件。
  • 失败时推送手机通知，同时返回空 token。
  • “诊断 stream” 可能是返回给客户端的一个特殊响应，用于排查问题。

这是可观测性（Observability）的良好实践：不是静默失败，而是主动告警 + 提供诊断入口。

十四、难点剖析与思考

14.1 JWT 的无状态性与撤销难题

JWT 是自包含的，服务端验证时不需要查询数据库。但这带来了一个难题：如何撤销一个尚未过期的 JWT？

Supabase 的解决方案是：

  • access_token 短期有效（1 小时），减少撤销需求。
  • refresh_token 长期有效但可撤销，登出时服务端使 session_id 失效。
  • 如果强制下线，服务端可以撤销 refresh_token，但已签发的 access_token 在过期前仍然有效。

这是一个权衡：无状态带来性能优势，但有状态才能精确控制撤销。

14.2 时间戳的服务器权威性

JWT 中的 iat、exp、amr.timestamp 全部由服务器生成，客户端无法篡改。这保证了：

  • 即使用户本地时间不准，Token 的有效期判断仍然准确。
  • 认证事件的时间记录可信，可用于审计。
  • 防止客户端通过修改时间戳来延长 Token 有效期。

14.3 Token 刷新与并发请求

在高并发场景下，多个请求可能同时发现 Token 即将过期，然后同时发起刷新请求。这可能导致：

  • 多个刷新请求同时到达 Supabase。
  • 由于 refresh_token 是一次性的，第一次刷新后旧的 refresh_token 失效，导致后续刷新失败。
  • 整个系统 refresh_token 失效，必须重新登录。

解决方案：

  • 单例锁：使用 Promise 单例，确保同一时间只有一个刷新请求。
  • 分布式锁：多实例场景下，用 Redis 的 SET NX EX 实现分布式锁。

谁拿到锁，谁负责刷新；拿不到锁的实例等待并读取刷新后的新 token。

  • supabase-js 内部已经处理了单进程内的这个问题，它会复用正在进行的刷新 Promise。

14.4 安全性思考

  • access_token 是 Bearer Token：谁拿到它，谁就能在有效期内冒充用户。因此绝不能泄露。
  • refresh_token 更敏感：泄露后可以长期换取新的 access_token，危害更大。且它是一次性的，管理不当会导致整个系统失效。
  • anon key 可以公开：它只是项目标识，不能用于冒充用户。
  • JWT 只能解码查看，不能篡改：签名会校验，修改 Payload 会导致验签失败。
  • HTTPS 必不可少：防止 Token 在传输中被窃取。

14.5 工程实践中的最佳做法

实践 说明
使用 supabase-js 自动处理存储、刷新、并发
启用 autoRefreshToken 避免手动管理刷新逻辑
设置合理的 JWT 有效期 默认 1 小时通常足够，可根据安全需求调整
启用 refresh token rotation 每次刷新生成新的 refresh_token，旧的失效
监控 Token 刷新失败 及时提示用户重新登录
不要在前端日志中打印完整 Token 避免泄露
refresh_token 只由服务端管理 前端只持有短期 access_token
分布式刷新加锁 Redis SET NX EX 避免多实例竞争
使用 expires_at 判断过期 比 expires_in 更稳定

14.6 这套设计的精妙之处

  1. 分层降级：六层链每一层都有明确职责，从最快到最可靠，最后兜底告警，是分布式系统的教科书式设计。
  2. refresh_token 单点管理：利用 refresh_token 的”一次性”特性，反推必须由单一权威来源管理，天然避免了多端竞争。
  3. 前端只推 access：油猴脚本不推 refresh 的决策，体现了对 Supabase rotation 机制的深刻理解。
  4. 可观测性：Bark 告警不是可有可无的装饰，而是把”token 失效”视为 P0 事件。

14.7 风险与改进建议

  1. .env.local 写入 bug：建议立即修正为 $NEW_REFRESH。
  2. Redis 读取判断 bug：应判断解析后的 $REFRESH，而非 $READ_RESULT。
  3. 缺分布式锁：多实例并发刷新会导致 refresh_token 失效，建议加 Redis 锁。
  4. 本地调试体验：六层链在本地开发时可能触发不必要的告警，建议加环境判断。
  5. 安全边界：油猴脚本权限较大，应确保只在可信环境安装。
  6. 备份策略：.env.local 覆盖前应先备份。

十五、总结

本文以 TryBox 应用为案例，系统性地梳理了 JWT 与 Supabase 认证机制的核心知识点：

  1. JWT 结构：header.payload.signature，Base64URL 编码，非加密，可解码查看但不可篡改。
  2. Supabase 签发证据：iss 指向 Supabase 项目，字段符合 Supabase Auth 规范。
  3. 关键字段：exp、iat、amr.timestamp、session_id 均由服务器生成，使用 Unix UTC 时间戳。
  4. 认证流程：客户端向 Supabase Auth 发起 OTP 登录，获取 access_token 和 refresh_token。
  5. Token 动态性：登录时确定会话，但 access_token 会定期刷新，session_id 通常不变。
  6. access_token 即完整 JWT：拿到 access_token 就等于拿到完整 JWT。
  7. 过期与续期：access_token 默认 1 小时过期，用 refresh_token 刷新；refresh_token 是一次性的（rotation）。
  8. 六层降级链：内存 → 用户配置 → Redis → refresh 刷新 → 旧 access 刷新 → Bark 告警，是分布式系统的核心设计。
  9. 双写策略：Redis（权威）+ .env.local（备份）+ 内存（缓存），并发现潜在 bug。
  10. 前端采集：油猴脚本重写 localStorage.setItem 钩子，只推 access 不推 refresh。
  11. 可观测性：Bark 告警 + 诊断 stream，失败时主动通知而非静默。
  12. 工程实践：使用 supabase-js 导入 session，启用自动刷新，用单例锁保护并发刷新，实现持续获取 stream。
  13. 难点思考：无状态与撤销的权衡、并发刷新、refresh_token 单点问题、分布式锁、安全性最佳实践。
